# DiskWeave architecture normalization

Normalize architecture into **operator-meaningful product semantics**.

Architecture supplies constitutional constraints and target intent.

Canonical OpenSpecs own current required product behavior.

`diskweave-semantic-reconciliation` determines current canonical semantic ownership and coherence.

Implementation and evidence test claims; they do not create semantic authority.

The normalization artifact is temporary campaign state. Keep only the structure needed to make the transition safe, resumable, and eventually removable.

# Detail budget

Add detail when omitting it could make a capable fresh agent:

* implement the wrong product behavior;
* cross an authority or correctness boundary;
* miss a semantic dependency, inherited obligation, or cross-cutting invariant;
* lose an independently advancing semantic through grouping;
* broaden a claim beyond its evidence;
* lose a refusal, preservation, compatibility, progress, authority, or lifecycle rule;
* perform unnecessary canonicalization;
* mistake target intent for current debt;
* or be unable to tell what remains unresolved.

Omit detail when it merely repeats deterministic repository relationships, semantic-reconciliation logic, source headings, ordinary engineering, reversible implementation choices, or campaign bookkeeping after durable authority exists.

There is no preferred capability count, ledger-row count, source-cluster count, OpenSpec-change count, or agent strategy.

# Authority and delegation

Keep these roles distinct:

* Current `openspec/specs/*/spec.md` owns current detailed required product behavior.
* A reviewed active OpenSpec change defines the target for work within that change until verified and synced.
* The active architecture supplies current constitutional/design direction under its declared authority boundary.
* A candidate architecture supplies target intent and constitutional constraints only; it does not silently override current OpenSpecs.
* Current implementation shows realized behavior, not semantic authority.
* Evidence limits claims; it does not manufacture missing semantics.
* Capability maps, ledgers, milestones, Beads, and reports are planning state.
* Historical architecture and archived changes are explicit archaeology only.

Never implement changed product behavior directly from candidate architecture prose.

A selected capability needs sufficiently precise reviewed OpenSpec target semantics before behavior-changing implementation.

A green readiness result proves consistency of semantics the repository currently models. It does **not** prove that every consequential semantic remaining only in architecture prose already has a durable home.

Treat deterministic architecture impact as review scope, not proof that an owner must change.

Use existing workflows instead of duplicating them:

* `diskweave-knowledge` for deterministic current context, relationships, architecture impact, history, affected paths, and readiness;
* `diskweave-semantic-reconciliation` for current canonical ownership, refinement/composition, contradictions, gaps, failure/uncertainty coherence, and dependent review;
* normal OpenSpec workflow for reviewed target semantics and coherent change boundaries;
* milestone planning only after a coherent operator capability or independently useful increment is selected.

Do not prescribe OpenSpec change names/count, speculative `req.*` IDs, `design.md`, task decomposition, Rust modules/types/files, reversible implementation choices, or agent orchestration.

## Semantic-reconciliation boundary

Normalization identifies architecture predicates, candidate current review surfaces, relevant invariants, inherited obligations, and important failure/uncertainty dimensions.

It does **not** decide canonical semantic ownership or completeness.

Before a consequential finding becomes terminal because of what current canonical semantics do or do not require, run bounded `diskweave-semantic-reconciliation`.

This includes conclusions equivalent to:

* current canonical semantics completely cover the predicate;
* a target predicate is genuinely additional to current semantics;
* current canonical behavior is contradictory or missing;
* an existing owner must evolve or a distinct owner may be needed;
* no current semantic debt exists for the reviewed scope;
* or a downward/source-retirement disposition is safe because current semantics are already complete elsewhere.

Treat the architecture predicate as **non-authoritative context**. Reconciliation establishes the current canonical system first, then whether that system entails the predicate, leaves a target delta, exposes current drift, or remains unresolved.

A larger architecture proposition may be fully determined by valid composition of independently owned semantic decisions without needing an umbrella owner.

Record only a compact reconciliation result and reproducibility anchor. Do not copy claim cards or reproduce the reconciliation algorithm in campaign state.

Related predicates may share one bounded reconciliation when they genuinely share one canonical closure and one semantic question. Do not force one review per ledger row.

# Three reasoning tests

These tests are normalization responsibilities.

They discover what must be reconciled; they do not replace semantic reconciliation.

## 1. Operator-closure test

A capability boundary is valid only when the operator-visible action it authorizes is usable truthfully and safely.

Do not authorize an action while deferring semantics required by the first action that may immediately follow it.

Examples:

* read/write publication must define enough immediate-write meaning to keep the next possible write truthful;
* destructive recovery must define or gate on authority, source preservation, and claim lifetime;
* minimum status required for safe action belongs in that capability even when broader status remains separate.

Scheduling, optimization, extended background work, and optional surfaces may remain later when they are not required for the earlier operator contract.

Prefer the smallest operator-closed capability.

If deeper analysis shows that two mapped capabilities cannot become usable independently, repair the map boundary. Do not recommend an unnamed partial combination.

Conversely, do not merge independently useful capabilities merely to enlarge the first slice.

## 2. Semantic-boundary test

Create a separate campaign row when semantics can legitimately advance independently.

Split when parts can have different:

* current-versus-target conclusions;
* reconciliation results;
* target progress;
* governance outcomes;
* transition owners;
* product decisions;
* applicability scopes;
* claim or compatibility consequences;
* or completion times.

Keep parts together when they share one semantic question, applicability scope, and lifecycle.

When uncertain, ask:

**Counterfactual removal:** If an optional/deferred profile or mechanism disappeared, would an adjacent rule still constrain the baseline?

**Scope:** Does the semantic constrain other operations or capabilities beyond the one that exposed it?

**Lifecycle:** Could one part become settled while another remains deferred, product-decision blocked, format-experimental, or otherwise unresolved?

Split if any answer requires independent disposition.

Common traps include:

* a baseline rule beside a deferred positive feature;
* current refusal/disagreement semantics beside a target metadata or format extension;
* a positive provenance/claim rule beside a separate non-authority rule;
* an optional integration beside baseline authority ceilings or non-claims;
* independently reconcilable artifact/recovery semantics beside product-decision-blocked retention policy;
* a local operation beside a cross-cutting authorization, fairness, progress, or lifecycle rule.

Do not split merely because the source uses several headings or mechanisms.

## 3. Transition-inheritance test

A new transition, epoch, recovery path, authority path, or publication rule must not silently bypass obligations already active before entering it.

For every behavior-changing target transition:

1. identify each current state/path that can enter it;
2. enumerate current blockers, pending obligations, indeterminate states, preservation duties, and retained claims that may still be live;
3. include those obligations in the bounded semantic-reconciliation and target-specification scope;
4. determine from accepted target semantics whether they survive, are satisfied, or are explicitly superseded;
5. keep unresolved inherited obligations visible in refusal or acceptance semantics.

Ask:

> Could a current-conforming implementation enter this target path and thereby bypass an obligation that would otherwise still apply?

If yes or unresolved, the target semantics are not closed.

A new architecture mechanism does not reset current semantic state merely because it introduces a new lifecycle.

# Initial-pass result

For a whole-roadmap normalization, produce one decision-oriented artifact with:

1. **Authority and current-versus-target posture**
2. **Operator/product capability map**
3. **Normalization ledger**

   * every marked `arch.*` invariant;
   * consequential unmarked semantics that remain open, target-only, deferred, disputed, cross-cutting, or independently advancing
4. **Independent source-coverage audit**
5. **Recommended next capability to reconcile**
6. **Consolidated unresolved register**
7. **Normalization-completion gate**
8. **Concise retrieval/resumption record**

These are campaign views, not permanent product taxonomies.

For a bounded future architecture delta, apply the same reasoning only to the affected semantic boundary.

# Campaign state without bookkeeping inflation

State common campaign facts once rather than copying them into every row.

## Inspection

Record whether the architecture semantic and relevant evidence were actually inspected.

`inspected` does not mean semantically reconciled, target-specified, canonicalized, implemented, evidenced, or governed.

## Detailed semantic posture

Use the smallest vocabulary that preserves the finding:

* **impact-mapped** — the architecture semantic and plausible current review surface are understood, but current semantic closure is not yet established;
* **current-entailed** — bounded semantic reconciliation establishes that current canonical semantics completely determine the architecture predicate, including valid composition where applicable;
* **target-delta** — reconciliation establishes the relevant current closure and the architecture adds or changes detailed product meaning;
* **ownership-or-scope-unresolved** — canonical meaning, ownership, architecture scope, or product scope remains unresolved;
* **deferred** — the positive future semantic creates no current baseline obligation;
* **non-normative** — removing the material loses no required current semantic or retained future boundary;
* **removed** — an explicit accepted decision intentionally withdraws the semantic and its consequences have been dispositioned.

`current-entailed` does not mean one requirement owns the whole architecture proposition.

`target-delta` does not mean current debt.

A preliminary pass may leave a likely conclusion at `impact-mapped`. Do not promote it merely from lexical similarity, implementation behavior, deterministic impact, or local reasoning.

## Target progress

For semantics requiring a transition, distinguish:

* **mapped** — target meaning and review surface are understood;
* **target-specified** — reviewed OpenSpec target semantics determine success, refusal, uncertainty, authority, relevant transitions, inherited obligations, claim limits, and immediately usable behavior, with required current semantic reconciliation complete;
* **canonicalized** — the target semantic has durable current canonical authority under normal repository rules.

Implementation and evidence remain separate.

## Invariant governance

For each retained marked `arch.*` invariant, separately determine whether the invariant itself has its intended durable governed home and valid current impact links.

Detailed behavior being `current-entailed` does **not** finish invariant governance.

## Transition owner

Record an actual OpenSpec change or other accepted transition artifact only when one exists.

Otherwise use `none`.

Never invent transition owners during impact mapping.

# Initial normalization workflow

## 1. Establish repository posture

Determine:

* current active architecture;
* settled target or bounded delta;
* current canonical OpenSpecs;
* deterministic architecture/invariant impact;
* current readiness;
* reproducible source/target identity or repository snapshot;
* and only the implementation/evidence needed to distinguish realized behavior or claim scope from target behavior.

Separate:

* current canonical posture;
* target intent;
* deferred intent;
* unresolved retained intent;
* implementation posture;
* evidence and important evidence non-claims.

Do not claim terminal current semantic closure without the required reconciliation result.

Lexical absence is supporting evidence, not proof of semantic absence.

## 2. Build the operator capability map

Use a small number of coherent operator outcomes.

Capability labels are local navigation only.

Prefer:

> Restart a complete array after reboot without an exhaustive scan while seeing exactly which protection is current.

Avoid:

> Implement protection epochs.

For each capability preserve:

* **Situation/outcome**
* **Safe claim**
* **Stronger claim refused**
* **Refusal/unknown behavior**
* **Dependencies**
* **Relevant architecture invariants**
* **Current-versus-target posture**
* **Hardest semantic join**
* **Deferred nearby behavior**

Keep dependencies acyclic.

Challenge each capability with at least one failure, restart, uncertainty, destructive-action, immediate-follow-on, inherited-obligation, or partial-progress story.

If the story exposes constitutional ambiguity, return it to architecture review rather than inventing a detailed answer.

After drafting the map, reapply the operator-closure test.

## 3. Review every marked invariant

Every stable `arch.*` invariant must be explicitly accounted for.

For each record enough to resume:

* identity and concise predicate;
* affected capabilities;
* direct versus inherited effect where material;
* detailed semantic posture;
* compact semantic-reconciliation anchor for terminal current-semantic findings;
* target extension, if any;
* invariant-governance state;
* unresolved semantic or governance question.

Maintain useful traceability in both directions:

* each capability identifies the invariants that materially constrain it;
* each invariant identifies the capabilities that must apply or re-evaluate it.

Do not create another reverse matrix merely for symmetry.

Use `direct` when the capability's own semantics may weaken, strengthen, consume, or make a claim governed by the invariant.

Use `inherited` only when the capability consumes a settled prerequisite carrying the invariant and no local semantic review remains.

Capability dependencies do not substitute for invariant applicability.

Do not make a current constitutional invariant target-only merely because a new operation must obey it.

## 4. Track consequential unmarked semantics

Marked invariants are not an exhaustive inventory of architecture product meaning.

Create unmarked campaign rows only for consequential semantics that remain:

* pending semantic reconciliation;
* target-only;
* ownership/product-scope unresolved;
* positively deferred and needing a durable boundary;
* positively established current debt;
* independent claim/evidence gates;
* cross-cutting normative rules;
* or otherwise independently advancing under the semantic-boundary test.

Do not create a row for every already-current source fragment.

An already-current fragment may be omitted from the open ledger when the source audit can point to an applicable reconciliation result establishing current entailment and no independent target question remains.

Split mixed cases using the semantic-boundary test.

A deferred positive feature must not swallow a baseline refusal, prohibition, authority ceiling, preservation rule, compatibility rule, claim boundary, or progress/lifecycle obligation.

## 5. Distinguish current debt from target or unresolved intent

Do not call something current debt merely because current semantic coverage has not been demonstrated.

Record `current-debt-independent-of-revision` only when:

1. accepted current authority already requires the semantic;
2. it is not merely target, optional, future, candidate, or historical intent;
3. bounded semantic reconciliation establishes missing or inadequate current canonical behavior.

Otherwise keep it target-only, deferred, ownership/scope unresolved, unresolved retained intent, or evidence-only as appropriate.

Candidate architecture alone cannot establish current debt.

Conversely, candidate non-authority must not hide independently established current debt.

When consequential scopes remain unreconciled, prefer:

> No current debt was positively established among the reconciled scopes.

Do not claim globally that no current debt exists.

## 6. Independently audit source coverage

The ledger does not prove its own completeness.

For whole-roadmap normalization or retirement, perform a separate beginning-to-end source walk.

Map each consequential normative cluster to:

* a marked-invariant finding;
* an open unmarked campaign row;
* an applicable reconciliation result establishing `current-entailed`;
* a retained deferral with no hidden baseline obligation;
* an explicit removal decision;
* a justified non-normative/history disposition;
* or an uncovered omission that must be added.

The audit verifies coverage. It is not a second semantic inventory.

For every downward disposition ask:

1. **Normativity:** Would deleting this material change success, refusal, authority, preservation, compatibility, progress/lifecycle, provenance, or allowed claim meaning?
2. **Boundary:** Would deleting an adjacent optional/deferred feature leave this rule applicable?
3. **Scope:** Does this rule apply outside the proposed destination row or capability?

If the disposition also depends on a claim about current canonical semantics, require the applicable semantic-reconciliation result.

If any challenge fails or remains unresolved, keep the semantic independently visible.

For bounded future deltas, inspect only the complete delta, affected invariants, changed entry paths/inherited obligations, and required current semantic closure.

# Ledger economy

Prefer one temporary ledger with two sections:

1. marked invariants;
2. consequential open/unmarked semantics.

The deterministic knowledge graph remains the authoritative complete relationship source.

Do not copy the full `constrains`, `requires`, `refines`, or dependent graph into campaign prose.

Do not invent permanent IDs for temporary source clusters.

Do not make a snapshot-specific row count part of durable completion.

Record exact current requirement identities when they anchor a reconciliation result or materially constrain the selected capability. Elsewhere prefer compact deterministic retrieval anchors.

# Select the next capability

Choose the next reconciliation slice by:

* operator value;
* true semantic dependencies;
* operator closure;
* bounded target scope;
* architecture importance;
* and the useful truthful claim it can eventually support.

The recommendation must name one capability boundary from the map.

If deeper analysis shows that boundary must absorb or release semantics to become usable, repair the map first.

For the selected capability go deeper than the overview map.

Include:

* concrete operator story;
* safe claim and stronger claim refused;
* relevant architecture invariants;
* architecture predicates requiring reconciliation;
* candidate current canonical review surface;
* inherited blockers/obligations at each entry path;
* target intent;
* refusal/uncertainty paths;
* explicit out-of-scope behavior;
* acceptance-level semantic questions;
* evidence tiers only where they constrain the eventual claim.

For storage/recovery slices challenge, where relevant:

* admission and writer authority;
* immediate post-publication mutation;
* pending recovery/integrity obligations;
* partial/uncertain completion;
* crash/restart;
* source and last-required-material preservation;
* existing integrity/checksum obligations;
* heterogeneous geometry/tails;
* bounded resources and refusal;
* truthful partial-progress status;
* cross-operation fairness/starvation;
* shutdown;
* abandonment;
* retry;
* resumed execution.

These are contract questions and reconciliation inputs, not pre-authored OpenSpec requirements.

Do not call the selected capability semantically closed or `target-specified` until its consequential current-semantic questions have completed bounded reconciliation and the transition-inheritance test succeeds against accepted target semantics.

# Consolidated unresolved and resumption state

Keep unresolved work in one place and separate:

* **product decisions** — defaults, optional surfaces, release scope, destructive policy;
* **semantic reconciliation questions** — unresolved current ownership, composition, conflict, failure, or scope;
* **architecture questions** — genuine constitutional ambiguity;
* **current debt** — only positively established pre-existing semantic debt;
* **unresolved retained intent** — normative architecture material whose current/target/deferred/obsolete status remains unknown;
* **evidence-only gaps** — semantics are owned but a desired claim tier is unproved.

At the end of a pass record only what a fresh agent needs to resume:

* source/target identity and repository snapshot;
* relevant readiness result;
* applicable reconciliation anchors;
* open invariant governance;
* genuinely open unmarked/cross-cutting clusters;
* capability progress;
* actual transition owners;
* source-exclusion status;
* and the next recommended capability.

# Advancing one capability

When advancing one capability:

1. start from its operator story and safe claim;
2. retrieve relevant invariants and current canonical context;
3. enumerate inherited blockers, obligations, indeterminate states, preservation duties, and retained claims at each entry path;
4. identify the consequential architecture predicates and current-semantic questions;
5. run bounded `diskweave-semantic-reconciliation`;
6. consume its ownership/composition, contradiction/gap, failure/uncertainty, and dependent-review conclusions;
7. classify the architecture relationship as `current-entailed`, `target-delta`, current debt, or unresolved;
8. resolve constitutional ambiguity before detailed target specification;
9. use normal OpenSpec workflow to determine the minimum coherent reviewed target transition;
10. preserve stable `req.*` identity when the same durable contract evolves;
11. create a new requirement identity only when reconciliation establishes an independently owned semantic decision;
12. record the actual transition owner;
13. rerun the operator story and transition-inheritance test against the reviewed OpenSpec target;
14. update only affected campaign findings.

Do not preselect split, merge, supersession, new owner, existing-owner evolution, or an umbrella composition requirement before semantic reconciliation establishes the correct ownership shape.

Implementation may expose missing transitions, inherited obligations, refusal semantics, status, observability, or architecture assumptions.

Treat that as feedback to the artifact that owns the issue, never as semantic authority.

The whole architecture need not be canonicalized before the first coherent capability can proceed.

Behavior-changing implementation of that capability may proceed once its reviewed OpenSpec target semantics are sufficiently precise.

# Normalization completion

The architecture source may leave ordinary current use only when:

> No consequential normative semantic depends on that source document as its only durable home.

Prove all of the following.

1. **Marked invariants** — every retained invariant has complete capability applicability, settled detailed semantics, a durable governed home, valid current impact links, and no remaining dependence on the retiring source.
2. **Unmarked semantics** — an independent source walk finds no consequential normative semantic without a justified durable current, canonicalized target, retained-deferred, deliberately removed, or non-normative disposition.
3. **Semantic reconciliation** — every terminal conclusion depending on current canonical meaning has a still-applicable bounded reconciliation basis; no umbrella owner merely restates valid composition, and no actual independent policy is left distributed across composers.
4. **Target semantics** — every behavior-changing target semantic relied on by implementation is canonicalized through normal repository rules.
5. **Transition inheritance** — no new path bypasses an unresolved current blocker, obligation, preservation duty, indeterminate state, lifecycle obligation, or retained claim without explicit accepted supersession.
6. **Cross-cutting and deferred boundaries** — no normative authorization, status, provenance, fairness/progress, claim, preservation, evidence, or lifecycle rule is stranded under one local capability or swallowed by a deferred positive feature.
7. **Fresh-agent readability and authority** — current canonical requirements, governed invariants, maintained decision material, durable deferred/removal records, and evidence metadata are sufficient to reconstruct required behavior and claim limits without the retiring source or historical/planning material as authority.
8. **Knowledge/review integrity** — current readiness is green and architecture-induced semantic/dependent reviews were resolved individually; bulk fingerprint acceptance does not substitute for review.
9. **Source-exclusion proof** — a repository-supported bounded reconstruction succeeds with the retiring source unavailable as ordinary semantic input while durable governed/deferred/removal material remains available. Record explicitly when this proof is premature or unattempted.
10. **Evidence honesty** — focused checks prove only the capability and evidence tier actually claimed. Documentation consistency is not behavior proof.

# Fresh-agent litmus

Normalization is incomplete if removing the source makes a capable fresh agent need it to answer an important question equivalent to:

* What does this state mean?
* When may this action proceed?
* What inherited obligation still blocks it?
* What must fail closed?
* What evidence authorizes recovery?
* What does this integrity/protection claim mean?
* What provenance permits the claim?
* What claim must be retired before destructive mutation?
* What does successful completion certify?

# Future architecture deltas

After the monolithic-roadmap era:

1. start from one bounded architecture delta;
2. identify affected invariants;
3. identify changed operator outcomes and entry paths;
4. discover inherited obligations;
5. run bounded semantic reconciliation for consequential current-semantic questions;
6. reconcile target semantics through normal OpenSpec work;
7. prove the delta is no longer the sole home of accepted meaning;
8. retire temporary campaign state.

Do not recreate a whole-system normalization campaign for a bounded change.

Ordinary requirement changes must not silently modify, contradict, add, or retire governed invariants.

# Forbidden shortcuts

Do not:

* decompose architecture by section number or create one capability/change per invariant;
* treat every `constrains` target as requiring modification;
* use capability dependencies as a substitute for explicit invariant applicability;
* infer current product truth from implementation, tests, evidence, or green readiness;
* infer current semantic ownership, composition, contradiction, or absence with a local substitute for semantic reconciliation;
* infer current debt merely because current entailment was not demonstrated;
* demand a new umbrella owner for a proposition already entailed by valid canonical composition;
* mark a mixed cluster terminal without applying the semantic-boundary test;
* let a deferred profile swallow a baseline rule or independently advancing semantic;
* bury a cross-cutting rule under the capability that first exposed it;
* let a new transition bypass unresolved inherited obligations;
* turn optional integrations or future profiles into baseline blockers;
* copy the complete relationship graph or reconciliation reasoning into campaign prose;
* create a permanent parallel semantic registry or stable IDs for temporary source clusters;
* make row count or source-heading coverage the definition of completion;
* let candidate architecture flow directly into behavior-changing implementation;
* require the entire architecture to normalize before the first coherent capability can proceed;
* or accept a source-retirement proof that still supplies the retiring source as ordinary semantic input.

# Quality test

A good pass lets a fresh agent answer:

> What can the operator safely do, what may DiskWeave claim, which governed invariants constrain the capability, which current canonical semantics have actually been reconciled as sufficient, which inherited obligations survive into the target path, which target semantics still need canonicalization, what remains unresolved or deferred, and what is the next coherent capability to reconcile?

If the answer requires reconstructing the campaign from conversation history, guessing from implementation, re-performing semantic reconciliation inside normalization, or rereading the architecture source for current required behavior, normalization is insufficient.
