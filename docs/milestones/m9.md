# Milestone 9 — Operator-Controlled Recovery and Safe Start

> **Planning status:** This milestone is an autonomous execution contract for a repository-aware implementation agent. It is not semantic authority. Current required behavior remains owned by current canonical OpenSpecs. Where this milestone identifies a semantic gap or deliberate behavior change, reconcile it against the current repository through OpenSpec before relying on it.

## 1. Directive

Deliver one coherent operator-visible recovery path through the real supported `dwv` CLI.

Milestone 9 SHALL leave DiskWeave able to:

1. inspect an existing array without changing correctness-critical state;
2. explain current lifecycle, access, member, parity, checksum, recovery, damage, and redundancy state without collapsing them into one misleading health bit;
3. run exhaustive read-only verification and report exact known, unreadable, unresolved, or conflicting damage;
4. preview the currently supported metadata-loss recovery without mutation;
5. apply that recovery only after current identity, topology, recovery, and verification conditions are re-established;
6. preserve refusal, blockage, definite failure, and uncertain/reconciliation-required outcomes as different facts;
7. create fresh recovery state without rewriting matching data or parity payloads when current canonical recovery semantics authorize that path;
8. expose and complete any new checksum baseline required by fresh recovery state;
9. prevent read/write service while that mandatory baseline or any other current admission prerequisite remains unsatisfied;
10. survive reopen with the persisted integrity evidence needed to interpret the current baseline; and
11. report an array online/read-write only after current admission succeeds **and** a supported frontend actually publishes it.

The primary happy path is:

```text
existing array with missing/untrusted recovery state
        ↓
truthful read-only inspection
        ↓
exhaustive read-only verification
        ↓
read-only recovery preview
        ↓
current revalidation + authorized recovery
        ↓
fresh recovery state
        ↓
required checksum baseline completion
        ↓
current writable admission
        ↓
actual supported frontend publication
        ↓
truthful final status
```

The refusal path is equally part of the milestone:

```text
ambiguous / stale / conflicting / unsupported / incomplete proof
        ↓
explicit classification
        ↓
stronger action refused or blocked
        ↓
no unauthorized mutation
        ↓
uncertainty preserved
        ↓
concrete safe next action
```

## 2. Why this is one milestone

The CLI and recovery work cross one consequential boundary:

> **When may an operator move an existing array from observation into newly proven writable service?**

A CLI refactor alone does not answer that question. A hidden recovery primitive does not give the operator a safe workflow. Fresh recovery state without a valid checksum baseline does not complete recovery. Passing admission without publishing a frontend does not make the array online.

The smallest coherent M9 slice therefore runs from **inspection to actual safe start**.

M9 does not productize every existing recovery, repair, rebuild, degradation, or diagnostic capability. It includes only the work needed to prove this path and its fail-closed alternatives.

### 3.2 Milestone 8 is baseline

M8 is complete in the reviewed repository snapshot. M9 consumes rather than reopens its boundaries, including:

- one canonical portable service request;
- stable-slot rather than collection-position member selection;
- explicit binding of opened stores to topology assignments;
- distinct assignment, role, coding-position, topology, and store identities;

- the rule that caller-supplied metadata-loss classifications cannot manufacture recovery authorization.

Do not fold unrelated M8 cleanup into M9 because nearby code is inconvenient.

### 3.3 Current M9-relevant implementation gaps

The reviewed snapshot exposes four dependencies that M9 must close or deliberately reconcile:

1. **Observational recovery inspection:** the existing SQLite open path may initialize or migrate state, so status cannot simply reuse it while claiming to be non-mutating.
2. **Uncertain recovery commit:** current semantics preserve lost/uncertain acknowledgement, but the concrete adapter does not yet complete the conservative reopen decision between exact prior state, exact proposed state, and unresolved state.
3. **Checksum-baseline admission:** fresh metadata-loss recovery can record that a new checksum baseline is required, but the current end-to-end service path does not yet prove that required baseline complete and reconstruct its current integrity authority after reopen before allowing writes.
4. **Admission versus publication:** portable service admission and platform frontend publication are separate. Current macOS has no supported general serving frontend, while Linux has a narrow current ublk publication profile.

These are milestone dependencies, not permission for the CLI to invent policy.

## 4. Scope arbitration

### 4.1 Included

M9 includes the behavior represented by:

```text
dwv status <array>
dwv members <array>
dwv scrub <array>
dwv damage <array> [...]
dwv recover <array>
dwv recover <array> --apply <plan-id>
dwv start <array> [--read-only]
```

Exact locator syntax, option placement, baseline-continuation spelling, parser structure, and other reversible interface details are delegated.

The milestone includes:

- human-oriented output by default and explicit structured JSON;
- one coherent observation/result boundary for human and machine rendering;
- multidimensional status;
- non-mutating array/member/recovery inspection;
- exhaustive read-only scrub and exact storage-level damage reporting;
- read-only recovery preview;
- stale-plan protection and current revalidation before mutation;
- the current all-data/single-P metadata-loss recovery path under its real canonical prerequisites;
- apply-time re-establishment of required exhaustive verification when prior observation no longer carries continuous authority;
- conservative uncertain-commit reopen/reconciliation;
- a supported path to establish the mandatory post-recovery checksum baseline;
- persistence/reopen of enough current integrity evidence to make that baseline meaningful;
- a read/write admission barrier while the mandatory baseline is incomplete; and
- actual supported frontend publication for the final online claim.

### 4.2 Deferred from M9 completion

#### Range-local degraded read for a present partially failing member

The recovery discovery accepted this direction, and v0.8 supports it, but current canonical degraded-read semantics are narrower. Expanding from a whole known-missing slot to an exact unreadable or uniquely known-bad range has its own independent correctness matrix and completion gate.

M9 must report current degraded behavior truthfully, but it does **not** require this semantic expansion.

#### Full production repair and replacement/rebuild workflows

M9 may report whether existing canonical owners consider such actions available, blocked, refused, or unsupported. It does not need to productize all of those mutations through the production CLI.

#### Diagnostics export

A bounded diagnostic artifact remains useful, but explicit JSON plus existing trace/evidence infrastructure is sufficient for the M9 recovery path. Earlier result contracts should remain suitable for a later diagnostics consumer.

#### SQLite support promotion

M9 may improve SQLite behavior and evidence without broadening its current support/durability claim. Any stronger claim requires separate evidence-backed semantic reconciliation.

### 4.3 Explicit non-goals

M9 does not add:

- generic `--force` / force-assemble behavior;
- degraded writes;
- P/Q or two-erasure recovery expansion;
- a validator certificate/receipt system solely to avoid a second recovery scan;
- automatic repair during scrub;
- filesystem paths as canonical damage identity;
- generic accepted-loss or “abandon this file” mutation;
- a friendly-name/control-database subsystem as a prerequisite for basic array targeting;
- a generic daemon, job, or operation-history framework;
- a TUI or broad serialization-format matrix;
- broad Linux frontend/profile expansion;
- a macOS serving frontend;
- physical power-loss certification; or
- unrelated Rust cleanup.

## 5. Settled product and architecture decisions

Do not reopen these merely because another implementation is easier. Reconcile them only if current canonical semantics or current repository evidence shows a material conflict.

1. **`status` is the primary operator hub.**
2. **Human output is the default; JSON is explicit and versioned.** TTY detection may affect presentation, not semantic format selection.
3. **Status remains multidimensional.** Lifecycle, current access, start eligibility, members, parity, checksum coverage, recovery obligations, damage, and redundancy remain distinct.
4. **Do not expose `Authority` as a normal status field.** Show its operator consequence.
5. **Current access and start eligibility are different facts.** A stopped array may be startable while current access remains `none`.
6. **`start` is the normal operator verb.** Assembly may remain architecture terminology.
7. **`recover` means recovery of DiskWeave state/history/lineage.** Ordinary damaged bytes remain repair/rebuild concerns.
8. **Scrub is exhaustive and read-only.** Diagnosis and repair availability remain separate.
9. **Paths are locators, not identity authority.** Discovery order never resolves ambiguity.
10. **Recovery preview is read-only.** A plan ID binds a proposal; it does not create current semantic authority or payload freshness.
11. **Apply revalidates current state.** Stale, ambiguous, incompatible, or conflicting evidence refuses before unauthorized mutation.
12. **A completed prior scrub is not automatically reusable mutation authority after its claims are released.** For the missing/untrusted-recovery path, apply must re-establish the required exhaustive verification unless one continuous session preserves the needed authority.
13. **The matching all-data/single-P recovery writes no data/parity payload.**
14. **A mandatory new checksum baseline blocks read/write service until current canonical completion is proven.** Newly calculated checksums do not retroactively prove historical correctness.
15. **Uncertain mutation outcome is not definite failure.** It remains uncertain until reconciliation proves the resulting state.
16. **`start` reports online/read-write only after actual supported frontend publication.** Admission success alone is not publication.
17. **No generic `--force`.** Operator confirmation cannot manufacture identity, generation, checksum, format, or recovery evidence.
18. **Production and demo/test paths must not contain parallel semantic implementations.**
19. **Range-local present-member degraded-read expansion remains outside M9.**

## 6. Semantic reconciliation obligations

These are the semantic questions M9 must resolve against the current repository. They are **not** a pre-authored OpenSpec change list.

The implementation agent should use the current knowledge/ownership workflow to identify the exact owners, refiners, dependents, and change boundaries before editing.

### 6.1 Observational inspection

M9 needs an observational path that can distinguish enough recovery state to drive status and planning without silently initializing, migrating, repairing, or claiming writable ownership.

At minimum, final behavior must distinguish:

- absent state;
- present supported state;
- corrupt/unreadable state;
- unsupported interpretation;
- migration required before writable use; and
- uncertain/reconciliation-required state.

Inspection must not turn one category into another.

**Likely semantic area:** recovery-state semantics plus the existing inspection/mutation security boundary.

### 6.2 Recovery preview versus apply authority

A proposal may describe what would be allowed **if** current facts still hold. Apply must establish that those facts still hold at the mutation boundary.

For missing/untrusted recovery state, a plan or scrub digest alone cannot prove that payload bytes stayed unchanged after a prior command released its claims. Unless continuous authority is preserved, apply must reacquire current claims and re-establish the exhaustive verification required by current metadata-loss semantics.

Do not invent a new certificate/receipt subsystem merely to optimize away that scan.

**Likely semantic areas:** metadata-loss recovery, recovery-state semantics, identity/topology, and application composition.

### 6.3 Uncertain commit reopen

When a recovery-state commit may have occurred but acknowledgement is lost:

```text
prior semantic state = P
proposed semantic state = Q
commit outcome uncertain
        ↓
release/discard process-local belief
        ↓
reopen and semantically validate durable state
        ↓
exactly P    → P remains authoritative
exactly Q    → Q may become authoritative after validation
anything else / unreadable / conflicting
             → reconciliation remains required
```

Generation equality alone is not proof of exact semantic equivalence.

The exact semantic comparison/fingerprint mechanism is delegated.

**Likely semantic area:** recovery-state semantics and its concrete adapter.

### 6.4 Baseline completion and writable admission

M9 intends this product invariant:

> **If current recovery semantics require a new checksum baseline, read/write service remains unavailable until the current baseline is complete under current checksum/integrity semantics.**

The implementation agent must reconcile:

- what current coverage counts as complete;
- which identity/profile/set/generation/validity facts must survive persistence and reopen;
- how partial/interrupted work is classified;
- how service open reconstructs current integrity authority from persisted evidence; and
- where the mandatory-baseline condition participates in writable admission without accidentally narrowing unrelated healthy arrays.

M9 does not prescribe new requirement IDs, storage schema shape, work scheduling, or exact owner/refiner structure.

**Likely semantic areas:** checksum plane, recovery persistence, and healthy portable I/O admission.

### 6.5 Admission versus publication

The portable/application layer may determine that requested access is admissible. The product must not report the array online until an actual supported frontend publishes successfully.

The current narrow Linux publication profile must remain narrow. Unsupported platform/profile is a product capability limitation, not proof that the array topology is intrinsically invalid.

**Likely semantic areas:** existing service admission and frontend adapter contracts.

### 6.6 Operator composition without duplicate semantics

The production CLI may own:

- command/product vocabulary;
- human rendering;
- structured schema/versioning;
- deterministic completeness rules; and
- process/exit mapping.

It must not own:

- member identity;
- topology validity;
- scrub classification;
- repairability;
- recovery authorization;
- checksum validity/completeness;
- plan freshness; or
- writable admission.

If the current repository lacks a clear application-level owner for composing those decisions into one coherent assessment/action result, M9 should establish the smallest coherent owner through OpenSpec. The milestone does not preselect its name, requirement IDs, number of changes, or whether a change needs `design.md`.

### 6.7 Expected OpenSpec impact, without pre-authoring it

Repository reconciliation is likely to find work in these areas:

| Area | M9 intent | Expected disposition |
|---|---|---|
| Operator/application composition | one coherent assessment/action result | may need a new or refined canonical owner if none exists |
| Recovery-state semantics | observational inspection; uncertain-commit reopen | likely semantic refinement plus adapter conformance |
| Checksum/integrity semantics | current baseline completion and persisted interpretability | likely semantic gap/refinement plus implementation work |
| Healthy portable I/O | mandatory-baseline participation in writable admission | likely deliberate admission refinement |
| Metadata-loss recovery | preserve current authorization and new-baseline obligation | primarily compose; change only if reconciliation proves a gap |
| Identity/topology | preserve fail-closed current authority | compose and test, not redesign |

## 7. Operator contract

### 7.1 Array targeting

M9 does not require a management catalog.

A CLI target may locate candidate array/recovery context. Resolution does not prove member identity. Ambiguous target resolution refuses rather than selecting by discovery order.

### 7.2 Human and structured results

Human output is operator-oriented. Structured JSON is an intentional product contract, not arbitrary serialization of internal Rust types.

Both render the same underlying semantic result.

Structured results must preserve at least:

- schema/version identity;
- result kind;
- stable semantic outcome/reason codes;
- stable IDs where appropriate;
- integer byte offsets/lengths; and
- deterministic completeness/detail behavior.

A successfully inspected degraded or recovery-needed array is still a successful inspection command.

### 7.3 Status

Status should answer, without requiring architecture knowledge:

```text
Can I use the array now?
Can I write to it now?
Could it safely start read/write?
Are required members present and recognized?
What is known about parity?
Are checksums current and complete?
Is recovery state missing, uncertain, or carrying an obligation?
What damage is known, unreadable, or unresolved?
How much protection remains?
What should I do next?
```

For a stopped but startable array, the semantics should resemble:

```text
State        Stopped
Access       None
Start        Read/write available
```

Do not report current read/write access until it is actually active.

### 7.4 Members

Default member output should center stable logical roles, current recognition, current locator where useful, and operator-relevant problems.

Do not expose assignment generations or raw evidence fields by default unless needed to explain a consequential refusal.

### 7.5 Scrub and damage

Scrub reports requested/completed scope, completeness, known bad ranges where independently established, unreadable/incomplete ranges, unresolved/conflicting mismatches, and repair availability only when an existing owner actually provides it.

Scrub performs no payload repair or recovery mutation.

`damage` exposes exact bounded storage-level findings. File paths are not canonical damage identity.

Advisory report retention is optional; loss or staleness of a report must not change correctness authority.

### 7.6 Recovery preview and apply

`recover` without apply is read-only. It explains the current recovery problem, applicable current recovery disposition, remaining proof, consequences, non-actions, baseline consequence, and a bounded proposal identity.

The supported apply path must:

1. validate the proposal sufficiently to reject malformed/unrelated input;
2. reacquire current claims;
3. reassess current identity/topology/recovery state;
4. refuse stale, ambiguous, incompatible, or conflicting state;
5. re-establish required exhaustive verification when prior observation no longer has continuous authority;
6. invoke current canonical metadata-loss authorization;
7. preserve zero data/parity payload writes for the matching all-data/single-P path;
8. preserve definite rejection/failure/uncertainty distinctly; and
9. return to a fresh assessment rather than treating command success as writable authority.

A pre-existing corrupt/stale/untrusted recovery artifact must not be casually destroyed before replacement state is successfully validated where preservation is practical.

### 7.7 Baseline continuation and start

After fresh metadata-loss recovery, the operator must have a supported path to complete the required new checksum baseline. The exact command/workflow shape is delegated.

Externally meaningful rules are fixed:

- baseline obligation is visible;
- partial remains partial after interruption/reopen;
- only current valid persisted evidence contributes to completion;
- current complete evidence is interpretable after reopen;
- newly computed evidence does not claim historical correctness; and
- read/write start remains blocked until current completion is proven.

`start` requests actual service. It reports online/read-write only after current admission succeeds and the supported frontend actually publishes.

These are execution slices, not preselected OpenSpec changes or crate boundaries. Each package should cross the needed semantics, application boundary, production CLI, rendering, tests, and evidence.

### WP-9.1 — Truthful observation through the production CLI

**Useful new claim**

> DiskWeave can inspect an existing array through production-shaped `status` and `members` commands without changing correctness-critical state, and can explain why stronger access is or is not currently available.

**Scope**

Deliver the minimum production CLI/application path needed for coherent observation:

- real production command parsing established through `status`/`members`, not a parser-only phase;
- one coherent array assessment rather than renderer-side joins across unrelated observations;
- non-mutating recovery-state inspection;
- current identity/topology assessment through existing owners;
- multidimensional status and exception-focused member reporting;
- human default and explicit versioned JSON from the same result; and
- stable command outcome classes needed by these observations.

**Acceptance evidence**

Prove at least:

1. healthy/stopped inspection changes no payload, parity, recovery generation, semantic manifest, migration state, or integrity state;
2. absent, corrupt/unloadable, and migration-required recovery state remain distinct and inspectable without mutation;
3. moved member, wrong object at old path, and clone/duplicate ambiguity follow current identity semantics rather than path/discovery order;
4. current access and start eligibility are not conflated;
5. degraded/recovery-needed inspection still counts as successful inspection; and
6. human and JSON render the same semantic classification.

**Review gate**

Before adding recovery mutation, verify that CLI/rendering code has not become a second owner of identity, recovery health, or writable admission, and that observational open truly cannot initialize or migrate correctness state.

### WP-9.3 — Read-only recovery preview and complete refusal semantics

**Useful new claim**

> DiskWeave can tell the operator whether the current metadata-loss situation has an M9-supported recovery path, what that path would change, and what proof apply will still require—without changing anything.

**Scope**

Deliver production read-only recovery preview over the current metadata-loss matrix, with bounded deterministic proposal identity, consequences, non-actions, missing prerequisites, baseline consequence, and exact unsupported/blocked/refused distinctions.

**Acceptance evidence**

Prove at least:

1. missing/untrusted recovery state with unambiguous required members identifies the supported path or exact remaining prerequisite;
2. proposal generation changes no correctness-critical state;
3. certificate-gated behavior remains gated by real current receipt/evidence semantics rather than caller claims;
4. unsupported/non-productized recovery cases remain explicit rather than generic errors;
5. identity ambiguity or insufficient verification cannot become `ready` through presentation logic;
6. prior scrub information may improve explanation but does not itself grant future payload freshness; and
7. the same bounded observed facts produce the same proposal meaning/identity.

**Review gate**

Review every statement that says `ready`, `verified`, or `safe`. Confirm it refers to a current observation or a conditional apply path, not future mutation authority.

### WP-9.4 — Authorized recovery execution and uncertain-commit reconciliation

**Useful new claim**

> The operator can apply the M9-supported recovery; DiskWeave either creates fresh recovery state from current exhaustive evidence, refuses before unauthorized mutation, or preserves uncertainty until reopen proves what persisted.

**Scope**

Deliver:

- proposal application with current claim acquisition/revalidation;
- apply-time exhaustive verification when required;
- fresh recovery-state creation through current metadata-loss authorization;
- zero data/parity payload writes for the matching supported case;
- conservative treatment of pre-existing untrusted recovery artifacts;
- definite rejection/failure versus uncertain commit behavior;
- release/reopen semantic reconciliation; and
- fresh post-operation assessment.

**Acceptance evidence**

Prove at least:

1. unchanged current all-data/single-P all-match state creates fresh recovery state with the required new-baseline obligation and zero data/parity payload writes;
2. changed identity/topology or current verification after preview refuses before false recovery authority is created;
3. incomplete/unreadable/ambiguous verification cannot create fresh authoritative state;
4. failed fresh-state publication leaves no false current state and does not casually destroy the only prior untrusted artifact;
5. definite commit rejection leaves prior state authoritative;
6. uncertain acknowledgement accepts exact validated reopened prior or proposed state only as current semantics permit, and anything else remains reconciliation-required; and
7. no dependent mutation proceeds from process-local belief while commit outcome is uncertain.

**Review gate**

This is the first major mutation boundary. Review semantic ownership, failure injection, persisted-state diffs, source preservation, and uncertain-outcome handling before later work may depend on “recovery completed.”

### WP-9.5 — Complete the new baseline and prove safe start

**Useful new claim**

> A freshly recovered array can establish a current checksum baseline that survives reopen; read/write service remains blocked until that baseline and every other current admission condition are proven; and `dwv start` reports online only after a supported frontend actually publishes.

**Scope**

Deliver the post-recovery bridge:

- one supported operator path to establish/continue the mandatory baseline;
- persisted integrity evidence sufficient for current semantic interpretation after reopen;
- correct partial/interrupted baseline state;
- current baseline-completion assessment;
- service reopen that reconstructs current integrity authority from valid persisted evidence;
- participation of the mandatory-baseline condition in current read/write admission through the correct owner;
- `start` consuming rather than recreating admission semantics;
- actual publication through the current supported frontend profile; and
- truthful unsupported behavior where no publication path exists.

**Acceptance evidence**

Prove at least:

1. absent or partial mandatory baseline cannot release read/write admission;
2. interruption/reopen cannot promote partial work to complete;
3. only current correctly bound valid coverage can satisfy completion;
4. complete current evidence survives reopen and reconstructs service integrity authority;
5. newly calculated checksums are not represented as historical proof;
6. unrelated healthy arrays retain their existing admission behavior unless another current owner blocks them;
7. current supported Linux publication occurs only after admission succeeds and only then reports online/read-write;
8. relevant state change before publication refuses without leaving a falsely reported endpoint;
9. current macOS or unsupported Linux profile reports capability limitation rather than fake online state or intrinsic topology invalidity; and
10. final status distinguishes actual current access from mere start eligibility.

**Final review gate**

Review the complete production path, neighboring semantic regressions, structured-output contract, and exact scope of live frontend evidence. M9 completion requires the product happy path and main refusal/uncertainty paths through production commands, not only internal unit tests.

## 9. End-to-end acceptance stories

These stories test interaction between work packages. Detailed local behavior remains owned by the package that proves it.

### 9.1 Core recovery-to-service path

For a supported single-P array with intact expected bytes but missing/untrusted recovery state:

```text
status/members
→ truthful stopped/recovery-needed assessment

scrub/damage
→ exhaustive read-only verification; no payload mutation

recover preview
→ current supported recovery path and consequences explained

recover apply
→ current claims/verification re-established
→ fresh recovery state created
→ mandatory new baseline visible

baseline continuation + reopen
→ current complete coverage established and still interpretable

start
→ current admission passes
→ supported frontend publishes

final status
→ online/read-write only now
```

### 9.2 Changed-world refusal

A proposal is created, then relevant identity/topology/recovery state or payload verification changes. Apply reassesses current facts and refuses or takes the newly authorized disposition; the old proposal alone never forces the old result.

### 9.3 Lost acknowledgement

A recovery commit outcome is uncertain. Dependent mutation stops. Reopen validates exact prior, exact proposed, or neither. Only exact validated current state becomes authoritative; otherwise reconciliation remains required.

### 9.4 Baseline interruption

Baseline work is partial, the process stops, and the array reopens. Partial evidence remains partial unless each record still satisfies current semantics. Read/write start remains blocked until current complete coverage is proven.

### 9.5 Unsupported publication

Portable admission may say requested access is safe while the current platform/profile has no supported publication path. `start` reports that limitation and does not fabricate online state.

## 10. Evidence strategy

Build evidence at the boundary each package changes.

### 10.1 Deterministic semantic/application evidence

Use deterministic tests for assessment, identity/refusal composition, scrub classifications, recovery dispositions, proposal staleness, operation outcome classes, baseline states, and admission results.

### 10.2 Real adapter reopen/failure evidence

Use the real recovery adapter for claims about non-mutating inspection, commit rejection, lost acknowledgement, reopen reconciliation, crash-releasing ownership, and any semantic migration introduced by persisted integrity evidence.

Process kill/reopen supports process-loss claims. It does not certify arbitrary physical power loss.

### 10.3 Checksum/baseline evidence

Prove complete-coverage derivation, invalid-evidence rejection, interruption/reopen conservatism, persisted-evidence rehydration, and the mandatory writable gate.

### 10.4 Production CLI evidence

Exercise the real production commands. Human tests should focus on causal operator language, consistency, consequences, and absence of misleading jargon. Structured tests should prove intentional versioning, stable semantic codes, deterministic completeness, exact integer ranges, and one underlying semantic result.

### 10.5 Live frontend evidence

A live run is required only for the claim that `dwv start` actually publishes a supported endpoint. Reuse the current accepted narrow Linux profile. Keep portable recovery/baseline/admission tests independent of Linux where possible.

Evidence claims must remain bounded to the actual mechanism/environment exercised.

## 11. Consequential outcome classes

Preserve these distinctions wherever a command/action can reach them:

- **success** — requested observation/action completed as defined;
- **usage/input error** — the request is structurally invalid;
- **semantic refusal** — current proof does not authorize the stronger action;
- **blocked/unavailable** — a current prerequisite prevents the action;
- **not supported** — the current product/platform/profile does not provide the capability;
- **definite failure** — the attempted operation definitively failed; and
- **uncertain/reconciliation required** — DiskWeave cannot yet prove whether a consequential effect committed.

Do not collapse uncertainty into failure or degraded array condition into command failure.

- whether safe interrupted baseline work restarts or reuses still-current records;
- whether baseline continuation is synchronous or bounded resumable work;
- progress rendering, batching, and internal concurrency; and
- reusable abstractions justified only after multiple real commands prove they are common.

Prefer the simplest implementation that satisfies current canonical semantics, the settled M9 decisions, and the evidence boundary.

## 14. Final completion gate

M9 is complete only when the integrated repository can make all of these cross-package claims truthfully:

1. An operator can move from `status` through verification, recovery, required baseline completion, and `start` using the production command surface for the supported M9 profile.
2. The same underlying semantic results drive human output, structured output, and action admission; the CLI does not become a second correctness engine.
3. Observation and planning remain non-mutating, while consequential recovery is current-state-bound and fails closed when proof is stale, ambiguous, incomplete, or conflicting.
4. The supported metadata-loss path can create fresh recovery state without data/parity payload writes, and uncertain persistence is reconciled rather than guessed.
5. A mandatory post-recovery checksum baseline remains meaningful across reopen and blocks read/write service until current completion is proven.
6. Actual online/read-write status requires both current admission and real supported frontend publication.
7. Main refusal paths preserve exact causal explanation, no unauthorized mutation, and the correct distinction between refusal, blockage, unsupported capability, definite failure, and uncertainty.
8. Deferred semantic expansions—especially range-local present-member degraded read, broad repair/replacement workflows, frontend-profile expansion, and stronger SQLite durability claims—have not been smuggled into M9.
9. Evidence claims are scoped to what the deterministic, adapter, process/reopen, and live frontend tests actually prove.
10. Current repository-required OpenSpec, knowledge/readiness, focused regression, workspace, documentation, and applicable live-evidence gates pass, and remaining risks/deferred work are recorded without becoming false completion claims.

## 15. Review question for every work package

At every review boundary, the implementation agent should be able to answer:

> **What useful new fact can DiskWeave safely claim after this work package, which current semantic owner supports that claim, what evidence proves it, and what still fails closed when the required proof is absent?**

If a proposed task cannot be connected to that question, it is probably infrastructure-first work that belongs inside a horizontal package rather than becoming a standalone phase.
