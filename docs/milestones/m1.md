# Milestone 1 — Runnable Honest macOS Demo

> **Historical planning record.** This milestone documents work sequencing and the authority model used when the work was performed. Current required product behavior lives only in current canonical OpenSpecs. Historical claims and instructions do not override current requirements or the active architecture roadmap.

## Goal

Take the current DiskWeave repository to a runnable, honest macOS demo grounded in `docs/architecture/archive/diskweave-architecture-roadmap-v0.6.md`.

Work autonomously through the repository's OpenSpec workflow: create or continue OpenSpec changes as work progresses, implement them incrementally, validate the artifacts and code, record executable evidence, and make coherent conventional `jj` commits with the reason for each logical change.

Do not edit the architecture handoff. Treat it and the accepted decisions it contains as the source of truth. Do not silently expand the product into Linux production work, a custom filesystem, or a stable on-disk format.

## Definition of a usable macOS demo

A developer or operator must be able to run documented commands on macOS to:

1. Create or open a disposable file-backed single-XOR-parity array using ordinary regular or sparse files.
2. Keep data payloads byte-compatible with conventional standalone images. Do not add DiskWeave headers, trailers, sidecars, hidden reservations, filesystem markers, or required metadata to data members.
3. Perform healthy reads, writes, and flushes through a narrow runnable CLI or demo process.
4. Stop and reopen the demo while preserving data, parity, topology, integrity, and recovery state.
5. Simulate one known missing data member and perform evidence-gated, read-only degraded reconstruction.
6. Rebuild the missing member into a distinct replacement target with deterministic bounded progress, durable checkpointing, readback/equation verification, interruption/resume behavior, and final verification.
7. Prove the rebuilt replacement is byte-identical to the reference and directly readable after DiskWeave closes.
8. Refuse dirty, ambiguous, stale, aliased, beyond-tolerance, or insufficiently evidenced recovery cases without mutating source media.
9. Demonstrate conservative behavior when recovery metadata is missing, corrupt, stale, or conflicting.
10. Report exact supported behavior and limitations instead of implying production durability.

The final result must be an end-to-end runnable demo, not merely a collection of tested libraries. It must include documented commands, a reproducible disposable fixture, focused behavioral tests, verification evidence, and an explicit unsupported-behavior list.

## CLI and daemon direction

The handoff names `dwv` as the administrative CLI and `dwvd` as the parity
process. Treat the command examples in the handoff as illustrative guidance,
not as an implementation checklist or a frozen command ABI.

Before implementing CLI code, create an OpenSpec change for a small
`macOS-demo-v0` contract. Pin only the externally observable minimum:

- binary entrypoint and invocation context;
- the first end-to-end workflow and its small command set;
- read-only, plan-only, and state-changing operation classes;
- versioned machine-readable result envelopes;
- exit-status and error-class behavior;
- fixture/config ownership and path-resolution rules;
- plan contents and confirmation matching;
- daemon-required versus offline-capable behavior.

Mark this contract experimental and demo-scoped. Keep the full production
command tree, long-term flag compatibility, daemon transport details, and
internal CLI implementation replaceable until the demo produces evidence.
Do not let implementation begin with an untracked or invented command surface.

For the first macOS demo:

- keep `dwv` a thin boundary over portable service, verification, recovery, and
  store seams;
- keep parity math, recovery authorization, topology decisions, and durability
  rules out of CLI argument handlers;
- start with the smallest command surface that makes the demo runnable and
  inspectable: structured status, state explanation, member/identity evidence,
  capability evidence, inspection, verification, rebuild planning, and the
  bounded demo workflow;
- make read-only inspection and planning useful without a daemon;
- put data-plane service behavior in a separate process or replaceable demo
  adapter rather than making the CLI the parity engine;
- use a versioned local control boundary for daemon interaction; do not expose
  SQLite layouts or Rust enum layouts as the operator protocol;
- provide machine-readable output as a versioned diagnostic boundary, with
  human-readable output derived from the same semantic results;
- report unsupported, stale, ambiguous, uncertain, and blocked outcomes
  distinctly, without logging payload bytes or private runtime handles;
- represent any state-changing workflow as an explicit plan containing the
  expected array/store identities, topology and recovery generations, ranges,
  evidence, persistent-state impact, and rollback limits before execution;
- require an automation-safe confirmation value that matches the displayed
  plan for any state-changing workflow;
- add command names and output fields through an OpenSpec requirement and
  acceptance test instead of growing an untracked command surface.

The first demo does not need to implement the entire illustrative operator
command list in the architecture handoff. It needs one coherent, documented
path from fixture creation through status, verification, degraded/rebuild
planning, execution, and evidence reporting.

## macOS scope and bridge policy

Prioritize the portable regular/sparse-file macOS path.

A live FSKit, DiskImages, or macFUSE bridge is a separate evidence-gated milestone. Attempt it only when the environment provides a matching toolchain and the required executable evidence can be collected for installation, signing, attachment, fixed geometry, synchronization, cache behavior, disconnect, restart, and cleanup.

If the bridge is blocked by toolchain, entitlement, privilege, signing, or host limitations:

- deliver the runnable file-backed demo;
- record the bridge as blocked or unverified;
- preserve the failure evidence;
- do not fake attachment behavior or claim live APFS support;
- do not infer FUA, controller-cache, power-loss, or production durability guarantees from successful host-file operations.

## Portable Linux seams

Build Linux seams now, but do not implement Linux in this milestone.

Portable semantic crates must remain independent of ublk, io_uring, FSKit, macFUSE, Tokio, SQLite schema types, filesystem paths, and Linux-kernel types. Keep these concerns behind replaceable adapters and semantic contracts such as:

- normalized block requests and frontend events;
- `RandomAccessStore` and store capabilities;
- `RecoveryStateStore`;
- topology snapshots and identity evidence;
- operation-slot ownership and backend I/O lifetimes;
- semantic transactions and action/result traces;
- deterministic simulator and trace-replay interfaces.

The macOS/file-backed implementation is an adapter, not the definition of portable semantics. Tests for portable behavior must run without Linux-only dependencies.

## Explicit non-goals for this milestone

Do not expand scope into:

- a custom filesystem or mergerfs replacement;
- a namespace database in the parity core;
- P/Q or two-erasure recovery;
- degraded writes or unprotected writes;
- online rebuild or online topology reshape;
- Linux ublk production integration;
- physical-device power-loss certification;
- a stable format-v1 claim;
- automatic repair without independent integrity evidence;
- multi-host or multi-initiator arrays;
- speculative abstractions, dependencies, or performance work without evidence.

Later work must receive its own OpenSpec change unless it is an implementation detail required by the current acceptance criteria.

## OpenSpec workflow

1. Inspect the current repository, active changes, archived prerequisites, handoff sections, and existing implementation before editing.
2. Use the repository OpenSpec CLI and skills rather than inventing a parallel planning process.
3. Create or continue one coherent OpenSpec change at a time.
4. Ground each proposal, design, spec, and task list in the relevant handoff decisions and prerequisites.
5. Specify observable requirements, positive and negative scenarios, failure behavior, migration consequences, and executable acceptance criteria.
6. Keep OpenSpec task checkboxes conservative. Mark a task complete only after implementation and evidence exist.
7. Update verification documentation with the actual commands, observed results, and portable/macOS claim boundary.
8. Validate OpenSpec artifacts before implementation and after changes.
9. Use the verification workflow before considering a change complete or archivable.
10. Archive only after all acceptance evidence passes and no critical issue remains.

Routine engineering decisions belong to the agent. Escalate only product-semantic or destructive decisions that cannot be resolved from the handoff and executable evidence.

## Validation and commit workflow

For every logical implementation change:

1. Run `jj status` first and preserve unrelated existing work.
2. Make the smallest coherent change that satisfies the current requirement.
3. Add focused behavioral coverage for every new observable contract, boundary, invariant, and failure path.
4. Run the narrowest relevant smoke test before broad validation.
5. Run the applicable formatter, targeted tests, workspace tests, strict Clippy, dependency inspection, metadata checks, and OpenSpec validation.
6. Record evidence before marking tasks complete.
7. Create one conventional local `jj` commit per coherent logical change. Use an accurate imperative subject and a body explaining why the change exists, what evidence supports it, and any known limitation.
8. Keep commits separable. Do not mix unrelated formatting, generated files, or speculative refactors into feature commits.
9. Do not push, publish, rewrite unrelated history, or archive without explicit workflow authorization.

A passing compile alone is not completion. A behavior is complete only when its end-to-end path and failure behavior are demonstrated.

## macOS fixture policy

Use only small disposable fixtures created for the current run or reference
fixtures explicitly designated for this demo. Before any host interaction,
establish the fixture root, ownership, expected image identity, destination
state, source access mode, mount-point ownership, and cleanup ownership.

Keep image files, mount points, recovery state, and logs under a generated
fixture root. Preserve that root and its evidence when a command or test fails.
Do not infer permission to use an existing path from an environment variable,
its filename, or the fact that a host tool accepts it.

Use the repository's existing macOS probe and acceptance-test procedure rather
than inventing host-storage commands. Keep image attachment and detachment
limited to the designated fixture or exported endpoint, use read-only access
for reference material, close all backing stores before independent attachment,
and verify source, parity, replacement, and mount identities at every boundary.

No demo step may alter image contents or host storage outside the owned
disposable fixture. If a required operation cannot be shown to be confined to
that fixture, pause and request approval. Do not add raw host-storage command
recipes to this goal; the procedure and the acceptance test are the authority.

## Approval boundaries

The agent may act autonomously on repository files, OpenSpec artifacts, local
tests, and owned disposable fixtures.

Pause and ask before any operation that requires elevated privileges, changes
machine configuration or installed extensions, targets an existing host
resource not explicitly designated for the run, creates an irreversible state
transition, or has ambiguous ownership or scope.

If a path, image, device identity, mount point, process, cleanup target, or
failure state is uncertain, stop, preserve evidence, and report the blocker.
Do not broaden the operation or infer approval from tool availability.

## Completion standard

The goal is complete only when:

- the macOS demo is runnable from documented commands;
- the healthy, degraded-read, rebuild, interruption/resume, reopen, identity-refusal, and metadata-loss paths have executable evidence;
- source and parity preservation is proven;
- replacement output is independently readable and byte-verified;
- portable semantic boundaries remain intact;
- OpenSpec artifacts and task status match the implementation;
- validation evidence and claim boundaries are recorded;
- local conventional `jj` commits explain the logical changes;
- no critical correctness, recovery, identity, safety, or overclaiming issue remains.
