**Exact intended change**

Implement the minimum persistent relationship model inside `canonical-semantic-ownership`.

#### Relationship syntax

Allow the conditionally required forward markers as one contiguous block immediately after the intrinsic requirement marker and before normative prose:

```text
<!-- dwv:req req.capability.stable-id -->
<!-- dwv:requires req.other-capability.prerequisite -->
<!-- dwv:refines req.owner-capability.owner-policy -->
```

Meanings:

- `requires`: the source requirement's own semantics depend on an independently owned semantic fact;
- `refines`: the target requirement owns the same underlying detailed operational policy and the source defines a narrower specialization or adapter realization of that policy.

Composition alone is not refinement. Every consequential relationship satisfying one of these definitions SHALL be authored; a requirement with no such relationship declares none. Semantic reconciliation determines the required edges. Deterministic tooling validates the authored representation and SHALL NOT infer a missing relationship from arbitrary English prose.

Do not add `owns`, manual backlink, policy-key, graph-node, or duplicate requirement records. A requirement’s intrinsic ID and canonical location remain its semantic identity.

#### Mechanical validation

Fail closed when:

- a target is not a current canonical requirement;
- an edge is self-referential;
- an identical edge is duplicated;
- the same source-target pair is declared as both relation kinds without an explicit parser error;
- the union of `requires` and `refines` edges contains a cycle;
- a current relation points to an active-change-only, archived, retired, or removed requirement;
- a retired current requirement remains referenced by current reviewed state, manifest, curriculum, Rust marker, maintained documentation, or relationship marker.

Diagnostics SHALL include source path, line, source ID, relation kind, target ID, and the smallest discovered cycle when applicable.

The checker does not claim that two English requirements are semantically equivalent or that an ownership choice is correct.

#### Derived views

Extend the knowledge object and context schemas to expose:

- outgoing `requires`;
- outgoing `refines`;
- derived `required_by`;
- derived `refined_by`;
- local semantic fingerprint;
- effective semantic/review fingerprint;
- reviewed outcome/reason;
- implementation/evidence links already supported by the repository.

Add:

```bash
cargo xtask docs knowledge ownership <requirement-id>
```

The command SHALL return the bounded facts above and a derived owner-before-dependent reading order. It SHALL not issue a semantic-consistency verdict.

Backlinks, capability aggregation, and the readable dependency/ownership view are generated from forward markers. Do not check in a manual backlink table.

#### Dependency-closure semantic re-review

Replace the current reviewed fingerprint behavior with an explicit two-level fingerprint:

1. **local semantic fingerprint** — a formatting-stable digest of the local requirement's normative prose and scenarios, excluding intrinsic and relationship marker comments and non-semantic formatting;
2. **effective semantic/review fingerprint** — a deterministic digest of the local semantic fingerprint, sorted outgoing `(relation kind, target ID)` pairs, and each target's effective semantic/review fingerprint.

Validate that the combined semantic graph is acyclic, then compute effective semantic/review fingerprints prerequisite-first. `docs/reviewed-requirements.toml` SHALL store the effective semantic/review fingerprint.

Consequences:

- changing an owner's local semantics makes every direct and transitive `requires`/`refines` dependent review-suspect even when dependent prose did not change;
- changing only formatting does not make dependents suspect;
- changing an edge changes the source's effective semantics and propagates to all semantic dependents of that source;
- changing only a review outcome or reason does not propagate;
- every stale requirement requires an individual semantic review and concrete reason;
- bulk acceptance remains forbidden.

Keep the authored graph sparse and consequential; do not suppress transitive invalidation merely to reduce review churn.

Bump the affected knowledge/review schema versions rather than silently changing the meaning of existing fingerprints.

`knowledge affected`, `docs check`, and readiness diagnostics SHALL name `semantic-prerequisite-changed` when this mechanism triggers.
