# Milestone 10 — Honest Portable Boundaries Before v0.9

> **Planning status:** This milestone is an autonomous execution contract for a repository-aware implementation agent. It is not semantic authority. Current required behavior remains owned by canonical OpenSpecs. M10 repairs current architecture conformance without selecting the Rust, crate, process, or composition architecture that the imminent v0.9 exercise will evaluate.

## 1. Directive and completion boundary

M10 makes the current portable execution path honest before v0.9.

After M10, DiskWeave can truthfully claim:

> The current portable service consumes mechanism-neutral store effects, portable recovery exposes semantic rather than SQLite-specific contracts, and live frontend publication consumes admitted semantics without selecting a recovery implementation. Exact failure, uncertainty, lifetime, authority, identity, and evidence behavior remains unchanged across those boundaries.

This is a dependency-direction and conformance milestone. It does not add a product capability or define the future architecture.

## 2. Why this is one milestone

The included findings break one end-to-end portability claim at adjacent boundaries:

1. service logic imports and calls the concrete file adapter instead of consuming a portable store effect;
2. portable recovery exports SQLite evaluation vocabulary; and
3. live frontend publication names a service fixed to the SQLite recovery adapter.

The first repair establishes an admitted service that is independent of a concrete store mechanism. The recovery and frontend repair then proves that the same admitted semantics can cross the live publication boundary without a concrete recovery choice leaking inward. Removing the unused recovery marker is local cleanup inside that second repair; it is not a separate outcome.

Each included package is necessary to the integrated claim. The store source-file size and the unresolved CLI phase boundary can both be deferred without making that claim false, so neither is an M10 completion dependency.

## 4. Current invariants that must survive

M10 preserves these current semantic boundaries regardless of implementation mechanism:

1. **Exact effects.** Every store operation preserves the requested range, exact completed ranges, success/short/failed/uncertain/duplicate disposition, stable error class when known, and only the persistence evidence actually established.
2. **Stable identity.** Array, topology epoch, logical slot, assignment, coding position, store identity and incarnation, operation, child operation, buffer generation, and watermarks remain distinct and are not reconstructed from collection order, path coincidence, or adapter-local identity.
3. **Bounded ownership.** Admission reserves bounded operation, buffer, submission, and related resources before protected mutation. Submitted work remains owned until terminal completion or explicit reconciliation permits release.
4. **Abandonment is not rollback.** Loss of frontend delivery interest does not cancel consequential media effects, reclaim resources early, retry an uncertain non-idempotent operation blindly, or make dirty/indeterminate state clean.
5. **Authority does not move with types.** Store adapters do not decide topology or recovery policy. Recovery implementations do not redefine semantic health or commit outcomes. Frontends do not manufacture admission, recovery authority, or publication identity.
6. **Fail closed on missing proof.** Missing, stale, partial, mismatched, unsupported, or uncertain evidence cannot authorize a stronger completion, fence, checkpoint, clean state, checksum validity, degraded action, writable admission, or publication result.
7. **Evidence remains scope-accurate.** Deterministic, file-backed, SQLite, and live Linux evidence retain their distinct claim boundaries.

M10 may change internal Rust APIs freely where the repository permits a clean cutover, but it does not change these semantics or their observable outcomes.

## 5. Scope and non-goals

### 5.1 Included

M10 includes only the work needed to:

- remove concrete file-adapter dependence from the portable service and every service-owned path that creates that normal dependency;
- make the current store/service seam usable without losing exact effects, bounded ownership, or request payload semantics;
- retain conformance evidence through the current file-backed path and an independent deterministic path;
- remove SQLite-specific evaluation vocabulary from the portable recovery public boundary while preserving portable recovery outcomes and all adapter evaluation evidence;
- remove the unused recovery marker if revalidation still finds no semantic consumer;
- make live frontend publication consume an already-admitted portable service without fixing the production-facing boundary to a concrete recovery adapter; and
- prove the integrated current file/SQLite/ublk composition without declaring where future composition must live.

### 5.2 Explicit non-goals

M10 does not:

- split the store hub as a standalone objective or choose module-versus-crate boundaries for v0.9;
- settle A6's pre-operator versus operator-result phase boundary;
- change CLI schemas, policy semantics, commands, exit behavior, or rendering;
- introduce a daemon, control plane, RPC boundary, executor architecture, backend family, plugin system, or other speculative v0.9 structure;
- freeze current trait names, dispatch strategy, payload-transfer API, fixture placement, composition root, process model, or package layout;
- add a production storage or recovery implementation merely to prove abstraction;
- change persistent formats, recovery authority, durability semantics, parity mathematics, checksum validity, degraded-read policy, writable admission, or supported frontend profiles; or
- broaden deterministic, file-backed, SQLite, macOS, or Linux evidence into a stronger platform or power-loss claim.

### 5.3 Deferred findings

A2 remains a maintainability and auditability observation, but broader store-hub decomposition is not an M10 objective. Local structural changes are permitted only when needed to complete the included conformance work safely.

A6 remains an unresolved externally observable CLI/operator semantic boundary. It requires a separate product/OpenSpec decision. M10 does not select or implement that decision.

## 6. Work packages

### WP-10.1 — Portable service execution over mechanism-neutral store effects

#### Useful new claim

> The admitted portable service executes current healthy, degraded-source, rebuild, and verification-related store work without importing a concrete store adapter, while preserving the exact request, outcome, evidence, and resource-lifetime contracts.

#### Scope

Repair the service/store boundary across every current caller needed to remove the normal service-to-file-adapter dependency. The resulting boundary must carry enough information and payload access to execute current reads, writes, flushes, and associated recovery/verification work without an adapter-specific downcast or a second source of operation truth.

The implementation agent owns whether this is achieved by repairing an existing seam, replacing an inadequate internal seam, moving adapter work outward, or another small architecture-conformant change. Current Rust types are evidence, not mandated target APIs.

#### Acceptance evidence

Prove all of the following:

1. The normal dependency graph and production service sources contain no dependency on file paths, file descriptors, file-store errors, or a concrete file-store type.
2. The current file-backed adapter and an independent deterministic implementation drive the same admitted service behavior for supported reads, writes, and flushes.
3. Exact request identity, topology epoch, member binding, ranges, child identities, dispositions, watermarks, and persistence evidence remain observable and comparable across both implementations.
4. Short completion, definite failure, uncertain media effect, duplicate/lost completion, stale generation, and resource exhaustion remain distinct; none becomes success through translation or retry.
5. Exhaustion occurs before protected mutation, and buffers, tags, slots, submissions, and reconciliation evidence are not released or reused early after abandonment or uncertainty.
6. Current publication identity, checksum-baseline admission, dirty/integrity transitions, degraded-source authorization, rebuild verification, and restart behavior retain their prior observable outcomes.
7. Request-boundary payload handling preserves current ownership, lifetime, bounded-resource, and allocation-accounting constraints. Any newly introduced payload copy is visible to the applicable resource accounting and cannot weaken operation identity, lifetime, or uncertainty semantics.

#### Validation gate

Before another package depends on the admitted service, reconcile the implemented boundary with current canonical owners for normalized requests, store effects, operation lifetimes, healthy service orchestration, recovery evidence, and checksum admission. A green type check is insufficient if exact uncertainty, persistence, or ownership evidence has been weakened.

No external user decision is expected. If current canonical semantics and implementation genuinely conflict, resolve that repository-local contradiction through OpenSpec rather than inventing M10 policy.

### WP-10.2 — Recovery adapter hygiene and mechanism-neutral live publication

#### Useful new claim

> Portable recovery and the live frontend boundary no longer expose or select a concrete recovery mechanism, while current SQLite evaluation and live publication behavior retain their bounded evidence and authority rules.

#### Scope

Move concrete SQLite candidate and failure vocabulary out of the portable recovery public contract while retaining the mechanism-independent recovery observations and conservative dispositions consumed by the rest of the product. Preserve the full declared SQLite evaluation matrix at the adapter/evidence boundary.

Remove the methodless recovery marker if revalidation still shows that it adds no semantic contract beyond the real recovery store boundary.

Change the live publication seam so it accepts admitted portable semantics without naming or constructing a concrete recovery implementation. Concrete adapter selection must remain outside the live frontend boundary, but M10 deliberately leaves the exact module, crate, binary, daemon, or process that performs composition to current repository planning and v0.9.

Disposable acceptance fixtures may still construct concrete file and SQLite mechanisms. They must remain visibly non-authoritative and must enter the same admission and live translation behavior they claim to test.

#### Acceptance evidence

Prove all of the following:

1. The portable recovery public API contains no types or configuration whose semantics encode SQLite journal mode, synchronization mode, checkpoint behavior, connection/schema/layout details, or SQLite-specific evaluation, reset, corruption, or candidate cases. Mechanism-independent recovery concepts remain portable even when similar terminology is appropriate.
2. The current file-backed adapter and an independent deterministic implementation both drive the admitted service through the repaired store boundary. Evidence covers supported reads, writes, and flushes and each current service-owned path category that materially changes store behavior, including degraded-source, rebuild, or verification paths where applicable. Equivalent backend outcomes produce equivalent portable semantic outcomes; mechanism-specific evidence need not be identical.
3. Every declared SQLite journal/synchronization/checkpoint/reset/failure candidate retains its prior expected outcome and evidence scope after relocation.
4. Memory and SQLite recovery implementations continue to satisfy the same semantic recovery boundary; moving types does not select a production SQLite profile or strengthen durability claims.
5. The unused marker declaration and blanket implementation are absent, unless revalidation finds a real semantic consumer that must instead be reconciled through current ownership.
6. Production-facing live publication types and control flow do not select or name a concrete recovery adapter and do not reconstruct admission from fixture, path, or local collection state.
7. The frontend continues to preserve stable target slot, full publication identity, request translation, bounded tag/buffer ownership, deterministic terminal mapping, shutdown, and cleanup behavior.
8. Unsupported platform, frontend profile, operation, flag, or durability intent remains explicit and is not reclassified as invalid topology or success.
9. Disposable fixture initialize, inspect, serve, trace, cleanup, and independent-data inspection retain their current bounded claims without becoming a second production authority path.

#### Validation gate

Reconcile the result with current recovery, healthy-service, normalized-request, and Linux publication ownership before accepting the package. Verify separately that:

- relocating evaluation vocabulary did not delete required adapter evidence or move semantic policy into SQLite code; and
- decoupling live publication did not move recovery/admission decisions into the frontend or a fixture.

No external user decision is expected.

## 7. End-to-end acceptance stories

### 7.1 Current composition through honest boundaries

At a composition boundary selected by the implementation agent, construct the current file-backed stores and SQLite recovery implementation, establish the current topology and evidence, and admit the portable service. Pass the admitted service to live frontend publication. The service does not import the file adapter, the live frontend does not select SQLite, and the published endpoint uses the exact admitted target and publication identity.

This story proves current composition across repaired seams. It does not establish that the chosen composition location or Rust representation is the v0.9 architecture.

### 7.2 Uncertain store effect survives to the frontend boundary

Through an independent deterministic store implementation, submit a current supported operation whose media effect becomes uncertain or whose completion is lost. The service preserves exact partial/uncertain evidence, retains owned resources through reconciliation, keeps required state dirty or indeterminate, and the frontend does not deliver success or infer rollback.

### 7.3 SQLite evaluation remains adapter evidence

Run the existing SQLite candidates across their declared synchronization, checkpoint, reset, missing-state, and corruption cases. Portable recovery supplies only semantic observations and dispositions. The adapter evidence remains conservative and does not certify physical power-loss behavior or select a production profile.

## 9. Evidence and claim boundaries

- Dependency-graph and source evidence proves direction and type separation, not behavioral equivalence.
- Deterministic evidence proves portable semantic behavior and failure preservation, not filesystem or hardware durability.
- File-backed reopen evidence proves only the declared file-adapter scope.
- SQLite candidate fixtures remain evaluation evidence, not physical reset or power-loss certification.
- Portable frontend tests prove translation and resource behavior. Only the applicable bounded live Linux workflow proves actual ublk publication.
- Fixture success never authorizes production topology, recovery, admission, or publication.

## 10. Final completion gate

M10 is complete only when these integrated facts hold simultaneously:

1. The portable service has no normal concrete store-adapter dependency and preserves current exact effects and operation ownership through file-backed and independent deterministic execution.
2. Portable recovery exposes no SQLite-specific evaluation vocabulary, while current semantic outcomes and complete SQLite adapter evidence remain intact.
3. The live frontend consumes admitted portable semantics without selecting a concrete recovery implementation, and current publication behavior remains truthful and bounded.
4. The unused recovery marker is removed after revalidation, or a newly discovered real consumer is reconciled without preserving a ghost abstraction.
5. Existing failure, uncertainty, identity, topology, persistence, abandonment, reconciliation, authority, and claim-boundary behavior has not weakened.
6. Focused conformance tests, workspace checks, applicable live evidence, OpenSpec validation, knowledge readiness, documentation checks, and a final architecture review pass.
7. The final dependency graph introduces no dependency cycle, replacement inversion, semantically empty replacement abstraction, or speculative v0.9 structure introduced solely to complete M10.
8. No broader A2 decomposition or A6 semantic change is introduced under M10.

At each work-package boundary, the implementation agent must be able to answer:

> What portable-boundary fact is now true, which current semantic owner supports it, what evidence proves it, and what failure or uncertainty still remains explicit?
