# Milestone 2 — Portable OpenSpec Execution

> **Historical planning record.** This milestone documents work sequencing and the authority model used when the work was performed. Current required product behavior lives only in current canonical OpenSpecs. Historical claims and instructions do not override current requirements or the active architecture roadmap.

## Mission

Maximize completed, evidence-backed OpenSpec milestones that can be implemented
now without Linux or a live macOS bridge.

Continue evolving the existing `dwv demo` CLI as the shared operator and
acceptance surface. Do not create a `v1` CLI, restart the command design, or
wait for Linux before completing portable work.

The goal is complete only after the agent has implemented and verified every
currently unblocked milestone in the queue below, not after the first runnable
workflow succeeds.

## Milestone queue

Work through these as separate coherent OpenSpec changes. Create or continue
the change, implement it, run its executable evidence, update verification
documentation, commit it conventionally, verify it, and archive it before
moving to the next one.

### OS-007 — parity-envelope profiles and independent decoder

Complete the skipped format-evidence milestone using disposable parity files.
Compare the bare, redundant-envelope, and envelope-plus-bitmap profiles without
calling any profile stable. Implement the smallest useful independent decoder
and exercise exact-capacity accounting, torn/disagreeing copies, unknown
features, migration, bounds, and hostile inputs.

The result must make a measured format choice or preserve a documented fallback;
it must not silently reduce protected capacity or turn the envelope into a
second transaction database.

### OS-009 — transaction-engine evidence comparison

Complete the skipped comparison between the explicit transaction machine and
the provisional `procmachines` direction, behind the same semantic action and
result contract.
OS-009 has a hard implementation gate before any broad refactor:

- add and compile the isolated `dwv-transaction-proc` workspace crate;
- pin and exercise the real `procmachines` dependency in a test;
- drive one representative semantic write through the procedural machine;
- compare its normalized actions, results, terminal state, and trace with the
  existing reference machine.

The first gate must be small enough to prove that `procmachines` is actually
being evaluated. Do not change `dwv-service` or replace the production
reference path merely to start the comparison. Service integration is a
follow-on decision after the evidence comparison.

 

Drive both with identical generated schedules and compare terminal states,
normalized traces, dirty/integrity decisions, uncertain completions,
abandonment, crash handling, resource behavior, dependency health, and
maintainability. Mutation cases must demonstrate that the comparison catches
premature clean/checkpoint, skipped invalidation, stale slot-token reuse, and
ignored uncertain completion.

Select the safer supported implementation or record a justified explicit-
machine fallback. An unavailable dependency or Linux-only environment must be
recorded as evidence, not become a blocker for the portable oracle and
comparison work.

### OS-017 — checksum scrub and verified repair

Connect the existing checksum, exhaustive-verification, repair, recovery, and
file-store implementations into the existing CLI.

The workflow must build independent data/parity evidence, scrub read-only,
classify data/parity/ambiguous/conflicting faults, create identity- and
generation-bound repair plans, reconstruct to a separate target, verify digest
and parity equation by readback, and preserve source media on refusal or
uncertainty.

Exercise induced data corruption, parity corruption, stale or absent evidence,
multiple suspects, failed target writes, interrupted repair, and stale plans.
Parity disagreement alone must never authorize repair.

### OS-024 — normalized trace fixture and replay

Implement a bounded, versioned, privacy-safe semantic trace at the normalized
portable boundary. Extend the existing CLI to export and render traces and to
replay them against the deterministic simulator and file-backed path.

Cover reads, writes, flushes, recovery intent/checkpoint, checksum work,
degraded reads, rebuild chunks, repair decisions, refusals, and uncertain
outcomes. Require deterministic final payload/parity/integrity/recovery state,
malformed and oversized-input rejection, schema migration, and minimized
failing traces.

## Integration outcome

As the milestones land, the existing `dwv demo` command surface must evolve to
support one honest disposable workflow:

```text
demo init
  -> healthy read/write/flush/reopen
  -> baseline and scrub
  -> induced fault and evidence classification
  -> verified repair or conservative refusal
  -> degraded read and resumable rebuild
  -> recovery metadata-loss handling
  -> trace export, rendering, and replay
```

Preserve existing commands where their semantics remain valid. Add only the
smallest commands needed for the implemented milestones. Keep machine-readable
results and exit statuses able to distinguish operation success from clean
state, mismatch, refusal, blocked, and uncertain outcomes.

## Boundaries

The architecture handoff and each milestone's OpenSpec artifacts provide the
normative details. Do not duplicate them here or invent alternate semantics.

Keep the implementation portable and file-backed:

- no Linux ublk, io_uring, or production daemon work;
- no FSKit, DiskImages, or macFUSE implementation unless the host explicitly
  passes the bridge entry gate;
- no physical-device or power-loss certification;
- no P/Q, degraded writes, namespace pooling, or stable format-v1 promise;
- no required metadata in ordinary data payloads;
- no automatic repair without independent verified evidence.

OS-021, OS-022, and OS-023 remain bridge/toolchain-gated. OS-030 and later are
Linux milestones and remain outside this goal. Record those blockers and keep
working on the queue rather than waiting.

## Autonomous execution rules

Routine choices belong to the agent: crate selection, bounded defaults,
SQLite settings, worker counts, trace limits, test fixtures, and transaction
implementation details. Use the architecture's accepted invariants and the
existing repository patterns.

For each OS change:

1. inspect its cited handoff sections, archived prerequisites, and existing
   implementation;
2. create or continue one focused OpenSpec change;
3. implement real behavior, not a scaffold or isolated type layer;
4. add focused tests for observable contracts and failure boundaries;
5. run the end-to-end CLI or simulator scenario that proves the change;
6. record actual evidence and the portable/macOS claim boundary;
7. verify and archive only after the artifacts and implementation agree.

Do not mark a milestone complete because code compiles or because a library
unit test passes. Do not stop the overall goal when one milestone is archived.

## Completion standard

This goal is complete when OS-007, OS-009, OS-017, and OS-024 each have
implemented behavior, executable acceptance evidence, coherent OpenSpec
artifacts, verification documentation, and archived changes; the existing CLI
exercises the integrated portable workflow; and no critical correctness,
identity, recovery, integrity, durability-overclaim, or dependency-boundary
issue remains.

## Next autonomous milestones after this goal

If the CLI and portable workflow are working, the agent can continue without
Linux on:

- topology add/remove/replace/resize transactions and replacement promotion;
- recovery-manifest export/import and all-data rebaseline after recovery-DB
  loss;
- control-plane jobs, maintenance checkpoints, and a versioned local
  administrative protocol;
- bounded scrub/rebuild scheduling and bandwidth policy;
- property/fuzz generation and automatic minimization of operation/fault
  schedules;
- file-backed macOS capability and synchronization characterization;
- larger-file benchmarks, allocation/write-amplification measurements, and a
  persistent trace/replay regression corpus.

The bridge-gated OS-021/022/023 sequence becomes eligible only when its host
entry conditions are met. Linux OS-030+ remains deferred until explicitly
opened as a later platform milestone.
